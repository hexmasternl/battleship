# Design

## Context

See proposal.md for motivation. Observed state: `src/` holds `Aspire`, `Games`, `Players` and `Frontend`. Games and Players each have four projects (`<Name>`, `<Name>.Abstractions`, `<Name>.Api`, `<Name>.Tests`) on `net10.0`; the API projects reference `HexMaster.Battleship.Aspire.ServiceDefaults`, call `AddServiceDefaults()` and `MapDefaultEndpoints()`, and still contain the template weather endpoint. The test projects use xUnit 2.9.3, `Microsoft.NET.Test.Sdk` 17.14.1 and coverlet. `AppHost.cs` registers the two APIs with `AddProject<>` and nothing else. The solution is `src/Battleship.slnx` with one solution folder per group.

ASP.NET Core 10 ships server-sent events: `TypedResults.ServerSentEvents(IAsyncEnumerable<SseItem<T>>)` writes `id`, `event` and `data` fields per item, serialises `T` with the configured JSON options and flushes per item (`System.Net.ServerSentEvents` provides `SseItem<T>` with `EventId`, `EventType`, `ReconnectionInterval`). Browsers provide `EventSource`, which reconnects automatically, sends the `Last-Event-ID` header on reconnect, cannot set other headers, and is closed by `close()`.

`issue-3-dapr-rabbitmq-pubsub` (a sibling proposal, not yet merged) models a RabbitMQ resource and a Dapr pub/sub component named `pubsub` in the AppHost and attaches Dapr sidecars to the API projects through the Aspire Community Toolkit Dapr integration. This change reuses that registration pattern and the component name; it does not define them.

The frontend is Angular 22 (`src/Frontend/`): standalone components, signals, `inject()`, Vitest through `@angular/build:unit-test`, an empty route table, and `src/Frontend/CLAUDE.md` rules (singleton services with the `@Service` decorator, no globals assumed in templates, `@if`/`@for` control flow).

## Goals / Non-Goals

**Goals:**
- One stream per browser tab, one envelope shape for every publisher, routing decided by the Events service alone from the envelope.
- Zero coupling between the Events service and game logic: it never inspects payloads.
- Identity resolution isolated behind one abstraction so `issue-7-user-identification` replaces a query parameter with a token claim without touching routing or the endpoint.
- Testable without Dapr running: the topic endpoint is a plain HTTP endpoint that the integration test can call directly.

**Non-Goals:**
- Multi-instance fan-out (a backplane such as Redis or a per-instance RabbitMQ queue). The replay buffer and connection registry are in-process.
- Durable event history. The replay buffer covers a short reconnect gap, not a page reload after minutes away.
- Authorization: who may listen to which game is enforced once identities exist (#7); this change trusts the supplied player id.
- Client-to-server messages. SSE is one-way; commands keep going over HTTP to the Games and Players APIs.

## Decisions

**Project layout mirrors Games and Players.** `src/Events/HexMaster.Battleship.Events.Abstractions` holds the envelope record and the `EventTarget` enum and has no dependencies, so Games and Players can reference it to publish. `src/Events/HexMaster.Battleship.Events` holds the routing core: `IConnectionRegistry` (player id to a set of connections), `IEventRouter` (envelope to connections), `IReplayBuffer`, each registered through an `AddEventsCore()` extension. `src/Events/HexMaster.Battleship.Events.Api` hosts the endpoints and the Dapr subscription. `src/Events/HexMaster.Battleship.Events.Tests` tests the core and the API in-process. Alternative considered: putting the SSE endpoint into the Games API; rejected because the Players service and future services would then push through Games, and the issue asks for a dedicated module.

**Envelope.** `IntegrationEventEnvelope(string Id, string Type, EventTarget Target, IReadOnlyList<string> TargetIds, DateTimeOffset OccurredAt, JsonElement Payload)` in Abstractions. `Id` is a publisher-generated ULID or GUID string. The Events service assigns the SSE `id` from a monotonically increasing per-process sequence, not from the envelope id, because `Last-Event-ID` replay needs an ordering; the envelope id travels inside `data` so clients can deduplicate. A `game` event lists its participants in `TargetIds`, so routing only ever needs the player id of a connection and the Events service keeps no game membership state. Alternative considered: Events service resolves game membership by calling the Games API; rejected as a runtime coupling and an extra hop per event.

**Dapr subscription.** `Dapr.AspNetCore` in the API: `builder.Services.AddDaprClient()`, `app.UseCloudEvents()`, `app.MapSubscribeHandler()`, and `app.MapPost("/integration-events", ...).WithTopic("pubsub", "integration-events")`. The handler validates the envelope (model binding plus explicit checks for id, type, target kind and non-empty target ids for `player` and `game`), hands it to the router and returns `200 OK` on both delivery and no-matching-connection; invalid envelopes return `400 Bad Request` with problem details, which Dapr treats as a drop with a warning in the sidecar log. Declarative subscription through `WithTopic` keeps the subscription visible in one place and lets the integration test post to the endpoint without a sidecar. Alternative considered: streaming subscription through `DaprClient`; rejected because it needs a running sidecar even in tests and has no cloud-events middleware story in the API pipeline.

**Stream endpoint.** `GET /events?playerId=<id>` returns `TypedResults.ServerSentEvents(stream)` where `stream` is an `IAsyncEnumerable<SseItem<JsonElement>>` fed by a bounded `Channel<SseItem<JsonElement>>` (capacity 256, `BoundedChannelFullMode.DropOldest`, with a warning log when a drop happens) owned by the connection. On connect: resolve identity, register the connection, enqueue replay items for `Last-Event-ID` if present, then yield from the channel until `HttpContext.RequestAborted` fires. Each event becomes `SseItem<JsonElement>(payload, eventType: envelope.Type) { EventId = sequence.ToString() }`. Heartbeats are `SseItem<JsonElement>(default, eventType: "heartbeat")` without an `EventId`, produced by a timer per connection every 15 seconds when nothing else was written; `EventSource` fires them as a named event the client ignores, and the write doubles as the liveness probe that detects a dead socket. Identity comes from `IConnectionIdentityResolver` with one implementation `QueryStringIdentityResolver` reading `playerId`; a missing or blank value yields `400`. Response buffering is disabled through `IHttpResponseBodyFeature.DisableBuffering()` and the endpoint is excluded from the standard resilience handler's timeouts (it is a server endpoint, not an `HttpClient` call, so only Kestrel's defaults apply; no keep-alive limit is configured). Alternative considered: hand-written `text/event-stream` writer; rejected because the framework result already handles field formatting, flushing and cancellation.

**Routing and registry.** `ConnectionRegistry` is a `ConcurrentDictionary<string, ConcurrentDictionary<Guid, Connection>>` keyed by player id, plus a flat set for `all` events. `EventRouter.Route(envelope)` computes the target connections (`player`: listed ids; `game`: listed ids; `all`: every connection), assigns the next sequence number, appends to the replay buffer and tries to write to each connection's channel. A write that fails because the channel is completed removes the connection; one failure never stops the loop. The sequence counter is an `Interlocked` long.

**Replay buffer.** A ring buffer of the last 1000 routed events (sequence number, envelope, target connection player ids) with a 2-minute age cap, guarded by a lock; replay for a reconnect filters by player id and sequence greater than `Last-Event-ID`. A `Last-Event-ID` older than the oldest entry falls through to live only. 1000 and 2 minutes are configuration values (`Events:Replay:Capacity`, `Events:Replay:MaxAge`) with those defaults. Alternative considered: no replay; rejected because a dropped connection during an opponent's turn would silently lose the shot.

**AppHost and CORS.** `AppHost.cs` adds `builder.AddProject<Projects.HexMaster_Battleship_Events_Api>("hexmaster-battleship-events-api")` with the same `WithDaprSidecar()` and `pubsub` reference the Games and Players APIs get from `issue-3-dapr-rabbitmq-pubsub`. The Events API registers a CORS policy allowing the origins listed under `Events:AllowedOrigins` (default `http://localhost:4200`) for `GET /events` so the Angular dev server can connect cross-origin; the policy applies only to that endpoint. Alternative considered: proxying `/events` through the Angular dev server; rejected because the dev-server proxy buffers responses by default and would break streaming.

**Frontend service.** `src/Frontend/src/app/events/events.service.ts`, a singleton `EventsService` (decorated as the frontend guidelines prefer for new singletons), wrapping the native `EventSource`. Public surface: `connect(playerId: string)`, `disconnect()`, `events$: Observable<RealtimeEvent>` (a `Subject` behind it), `state: Signal<'disconnected' | 'connecting' | 'open' | 'reconnecting'>`. `connect` is idempotent per player id; a different player id disconnects first. The service listens to `open`, `error` and a wildcard of known event types: because `EventSource` only dispatches named events to registered listeners, the service registers listeners for the event types published in `realtime-event-types.ts` (a string union exported from the feature folder and kept in step with the Abstractions project by hand) and treats `heartbeat` as a no-op. `error` while `readyState` is `CONNECTING` maps to `reconnecting`; `readyState` `CLOSED` maps to `disconnected`. The Events API base URL comes from an `EVENTS_API_URL` injection token provided in `app.config.ts` with the Aspire-assigned development URL as default. `inject(DestroyRef)` on the root injector closes the stream on teardown. Tests replace `EventSource` with a fake through an injection token `EVENT_SOURCE_FACTORY`. Alternative considered: `fetch` with a streaming body parser to allow an `Authorization` header; rejected for now because `EventSource` gives reconnection and `Last-Event-ID` for free, and #7 can pass the token as a query parameter or cookie.

**Tests.** xUnit in `HexMaster.Battleship.Events.Tests`: router and registry rules (one test per spec scenario), envelope validation, SSE item mapping (id, event, data), replay filtering and overflow, heartbeat timing with a fake time provider (`TimeProvider`). An in-process integration test with `WebApplicationFactory<Program>` opens `/events?playerId=A` through `HttpClient` with `HttpCompletionOption.ResponseHeadersRead`, posts an envelope to `/integration-events`, and asserts the parsed SSE message within one second; `UseCloudEvents` accepts plain JSON with `application/json`, so the test does not need a cloud-event wrapper. Vitest for the frontend service with a fake `EventSource`. The Dapr round trip (RabbitMQ through the sidecar) is verified manually with `dapr publish` against the running AppHost and recorded in the README.

## Risks / Trade-offs

- [`issue-3-dapr-rabbitmq-pubsub` names the component or the sidecar helper differently from what this design assumes] -> the AppHost task reads the merged AppHost before adding the Events API and follows whatever pattern is there; the component name `pubsub` and topic name `integration-events` are the only hard contracts and are configuration values in the API.
- [Two Events API instances would each see only their own connections] -> explicitly out of scope; the AppHost runs one replica and the README states the limitation. A backplane is a later change.
- [`EventSource` cannot send an `Authorization` header, so #7 may need a different transport for the token] -> identity resolution is one interface on the server and one URL builder on the client; switching to an `access_token` query parameter or a cookie touches only those two spots.
- [A slow client fills its channel] -> bounded channel with drop-oldest and a warning; the client still gets the newest state and can resync through its own HTTP reads. Capacity is configurable.
- [Named events require the client to know every event type ahead of time] -> the type list lives in one file per side; a new event type is a two-line change. The service also logs unknown `message` events so a missing registration is visible.
- [The dev-server CORS origin differs per developer] -> `Events:AllowedOrigins` is configuration; the default covers the Angular CLI port.
- [Kestrel or a reverse proxy closes long requests] -> the 15-second heartbeat keeps the stream below common idle timeouts; Kestrel has no request duration limit by default.

## Open Questions

- Whether the frontend should connect automatically at application start or only once a player enters a game. The service exposes `connect`/`disconnect` either way; the decision belongs to the first screen that needs events, not to this change.
